# Market catalog service — Build Card and implementation spec

Workstream: WS-023. Build OS: v0.12. Date: 2026-10-05.
Status: Approved direction; Calvin approved D1–D9 A and explicitly requested the Railway service and data migration in ChatGPT on 2026-10-05. Implementation actor: Codex. Solo mode; merge acceptance remains the owner's.

## Build Card
Goal: one comparable, queryable catalog for existing and newly discovered series, events and markets, with reusable evidence assessments for MMSELL and future strategies.
Current: registry, taxonomy and trading evidence are separate. New: a standalone Railway service owns a persistent catalog, imports legacy evidence without changing it, discovers Kalshi listings, detects semantic changes, and exposes versioned facts, reviews and assessments over an authenticated API.
Approved choices: separate completion/maturity/confidence/edge; separate paper/live; confidence qualification; recent/history views; known-template validation with human review for unknown changes; event refresh plus daily repair; broad catalog/selective telemetry; frozen experiments; separately authorized live canaries.
Important rules: no inherited profitability, no paper-to-live promotion, unknown stays unknown, immutable assessment snapshots, exact rules hash review, no writes to source database or trading permissions. Numeric qualification floors remain uncalibrated, so confidence and established-live qualification are initially withheld.
Done: persistent catalog, resumable idempotent import, bounded discovery and reconciliation, strategy evaluator interface, query/review API, tests and Railway deployment with verified backfill progress.

## Impact plan — before implementation
This release adds an isolated evidence/documentation service. It does not replace a declared XOS platform component, change any existing metric definition, taxonomy, risk, strategy universe, scientific contract or pinned snapshot. Source values are labeled legacy observations, not adopted semantics. No active experiment consumes the new API. Accordingly no Platform Revision is activated or substituted in this release. The source connection uses read-only transactions; the new service writes only its own volume.
Consumer cutover is a separate Platform Change Review: register a pending revision through the canonical worker transport, discover affected experiments from pinned snapshots, classify and accept impacts, and activate at a measured boundary only with explicit operator approval. Do not represent this import as that cutover.

## Spec
Owner decisions: D1–D9 A in MARKET_REVIEW_PIPELINE_PROPOSAL.md. Internal storage, pagination, retry and API mechanics are implementation discretion.
R1: series/event/market objects preserve raw payload, identity, first-seen versus exchange-created timestamps, legacy classification, rules fingerprints and revisions. Close, expected determination, settlement timer and observed settlement remain separate; unknown observation/payout timing is null.
R2: required structured semantic fields include resolution mechanism, observation window, alternatives/operator/exclusions, payout relationship, shared exposure and risk components. Only explicit human review supplies these; no language heuristic authorizes a classification. Legacy signatures remain provenance.
R3: exact reviewed template fingerprints may validate identical rules on the same series; new or changed rules require review. Changing semantic fields invalidates review; old revisions survive.
R4: source reads are SELECT-only, server-side transaction_read_only and statement timeout, bounded keyset pagination. Local import and cursor commit together; initial pass is followed by daily full reconciliation to catch settlements/updates. Preserve source IDs, deployment-arm lineage and paper twins separately. Never infer live P&L attribution from account positions.
R5: assessments isolate strategy/version (operational tag), deployment arm, series, side, entry band, fill policy, paper/live and window. Event clustering is conservative and labeled provisional; cross-series independence is not claimed. Recent and historical views remain distinct. Each snapshot preserves inputs/method/as-of and qualification reasons. Missing calibration or forward validation blocks confident scores.
R6: evaluator registry allows additional strategies without schema changes. MMSELL evaluator estimates reported paper net cents/contract (source pnl already net of fees), actual live fill coverage, active days and distinct provisional outcome groups. Twins are paired-only and not scored as independent paper.
R7: discovery has persisted cursors, bounded work per loop and restart-safe retries; periodically restarts complete reconciliation. Fetch series and events/markets from public REST; no order credentials or order calls. WebSocket acceleration is deferred; REST is the recovery source.
R8: HTTP API has health/status, catalog, revisions, review queue, reviews and assessments/selection. Every data endpoint requires a bearer token; health reveals no sensitive evidence. Selection is advisory and never changes a universe. Review writes require actor, rationale, current hash and all required semantic fields.
R9: single replica SQLite WAL on a Railway volume; existing Postgres is read-only input. Deployment pins the tested commit on the PR branch so existing workers are untouched. Backup before future storage migration; no destructive legacy migration.
Failure behavior: failed source/discovery operation records sanitized error type and retries next loop; cursors do not advance past an uncommitted page. Readiness exposes last successful jobs and initial/reconciliation coverage. API validates bounds, stale review fails 409, malformed review fails 400, unauthenticated fails 401. Shutdown stops background thread before closing.
Acceptance: tests for crash replay, rule invalidation, exact template review, twin exclusion, context isolation, paper/live tiers, recent/history, unknown fields, API auth and source read-only SQL. Verify deployed health and logs with object/evidence counts. No live exposure or experimental lifecycle action.

Deployment adjustment: new Railway services reject legacy config files; use direct service settings. Automatic approval review rejected the owner Postgres URL. The service will deploy without it; approved read-only exports can seed evidence, while continuous source import awaits the scoped read-only URL.
